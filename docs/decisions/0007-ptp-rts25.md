# 0007 — PTP IEEE-1588 as RTS-25 Substrate

* Status: Accepted
* Date: 2026-05-04
* Deciders: Architecture Review Board
* Constitution: Principle IV (Time-Sync as First-Class)

## Context and Problem Statement

MiFID II RTS-25 (Art. 50) caps clock divergence from UTC at 100 µs for trading systems and 1 s
for everything else. NTP — at best 1–5 ms over the public internet — cannot meet that ceiling.
We need a sub-microsecond synchronisation substrate that survives audit and that we can
demonstrate annually with a tamper-evident report.

## Decision

* PTP IEEE-1588v2 boundary clocks per cabinet, fed by a Meinberg LANTIME M3000 grandmaster
  with GPS as primary and GLONASS as secondary reference.
* Solarflare / Mellanox NICs in trading servers with hardware timestamping (`ptp4l` + `phc2sys`).
* Daily PTP / NTP logs ship to OpenSearch (`ptp-logs-*`) via Vector.
* Annual audit pack generated by [`tools/ptp-audit-report/`](../../tools/ptp-audit-report/),
  signed with cosign, submitted to FINMA.
* Domain code reads time exclusively via [`libs/time-sync/RegulatoryClock`](../../libs/time-sync/);
  ArchUnit fitness function blocks any `System.currentTimeMillis()` call outside `libs/time-sync/`.

## Alternatives Considered

* NTP-only — rejected: ceiling violation likely under any network blip.
* PTP without HW timestamping — measured drift > 50 µs under load, leaves no headroom.
* White Rabbit (sub-ns) — over-engineered for our latency profile and operationally opaque.

## Consequences

* Meinberg appliance is a hardware purchase per region.
* Network team owns boundary-clock configuration; any new switch hop must support PTP-aware
  forwarding, otherwise we lose ~5 µs per hop.
* 50 µs warn-alert in [`ops/prometheus/alerts/ptp-divergence.yml`](../../ops/prometheus/alerts/ptp-divergence.yml)
  triggers BEFORE we breach RTS-25.
