# Swiss Trading & Market Support Platform Constitution

This constitution governs the design and engineering of the Swiss Trading
& Market Support Platform (the "Platform"). It supersedes any informal
practice or precedent. Compliance is verified at every pull request and at
every architecture review; deviations require explicit, documented
justification.

## Core Principles

### I. Hexagonal Adapter Discipline

Every venue, clearing house, market-data vendor, regulator-facing reporting
endpoint, identity provider, and external system MUST be implemented as an
outbound adapter behind a port interface defined in `libs/domain-model/`.

The domain core MUST contain **zero** venue-specific protocol details: no
FIX tags, no SBE / FIXML / FpML schemas, no BLPAPI / EMA / Pixie / Puffin
identifiers, no CFETS proxy artefacts, no AMQP message bodies. These types
live exclusively inside the adapter that owns them.

Adding a new venue MUST be possible by writing one new adapter implementing
the existing port; the OMS, EMS, reconciler, reporting service, surveillance
service, entitlements service, and any other domain-side service MUST
remain unmodified. Code-ownership boundaries (CODEOWNERS / module
visibility rules) enforce this in continuous integration.

**Rationale**: This is the central architectural commitment of the
Platform. It is what allows the system to mirror the publicly-documented
stacks of UBS, RBC Capital Markets, HSBC Equities, Man Group, and SIX
Interbank Clearing without entangling domain logic with vendor lock-in. A
breach of this principle invalidates the platform's portfolio claim and
its operational extensibility.

### II. Latency-Hierarchy Discipline

The Platform recognises three latency tiers; every component MUST be
placed in exactly one tier. Mixing is forbidden.

| Tier | Transport | p99 budget | Examples |
|------|-----------|------------|----------|
| **Hot** | Aeron IPC + Disruptor + SBE; Aeron Cluster (Raft) for replicated state | < 100µs (target < 30µs in co-lo) | EMS matching, pre-trade risk gateway, hot-path venue adapters |
| **Warm** | Aeron UDP / Solace / IBM MQ Low-Latency | < 5ms | OMS↔EMS, drop-copy fan-out, intraday position update |
| **Cold** | Kafka + Postgres + S3 | seconds | Surveillance, regulator reports, EOD reconciliation, TCA, backtesting |

Code in a hot-tier service MUST NOT make warm-tier calls in its hot path.
Warm-tier code MUST NOT use cold-tier transports for state that hot-tier
consumers depend on. Cross-tier ingress is permitted only at well-defined,
documented boundaries (for example, the inbound-FIX-acceptor publishes
into hot-tier Aeron IPC after a single explicit handoff).

**Rationale**: The Platform's tick-to-trade and pre-trade-risk latency
targets are unattainable if a hot-path component pays a Kafka or Postgres
round-trip. Tier discipline is the only way to keep latency budgets
predictable under sell-side prime broker load.

### III. Schemas-as-Versioned-Contracts (NON-NEGOTIABLE)

Every external message schema — FIX dictionaries, FIXML XSDs, FpML XSDs,
SBE schemas, Avro schemas in the Apicurio Registry, gRPC `.proto`,
OpenAPI YAML, ISO 20022 templates, GMRA legal templates — MUST be stored
in source control under `contracts/` and versioned using a documented
scheme (Avro `vN`, SBE schema id + version, semantic versioning for
proto/OpenAPI, file-name versioning for FIX dictionaries).

Any pull request that changes a schema MUST also:

1. update or add a contract test (Pact, jqwik, Hypothesis, JAXB roundtrip,
   SBE roundtrip — whichever applies);
2. include a brief change-summary in the relevant ADR or open one if the
   change is architecturally material;
3. demonstrate backward-compatibility evidence appropriate to the schema
   (Apicurio compatibility mode `BACKWARD_TRANSITIVE` for Avro;
   coexistence-for-one-trading-day commitment for breaking changes).

Custom FIX tags MUST be registered in `contracts/fix-sessions/dictionaries.md`;
a CI test enforces that no two contexts use the same custom tag with
different semantics.

**Rationale**: Trading platforms historically suffer from "tag X is now
also taken" regressions. Treating schemas as versioned, source-controlled
contracts with mandatory test coverage is the only mechanism that
prevents these regressions deterministically.

### IV. Time-Sync as First-Class

The synchronised regulatory clock provided by `libs/time-sync/` is the
single source of truth for any timestamp that flows into a regulator
report, an audit-chain entry, a surveillance event, a CCP confirmation,
or a venue order/execution.

Domain code MUST NOT call `System.currentTimeMillis()`,
`System.nanoTime()`, `Instant.now()`, `LocalDateTime.now()`,
`time.time()`, `time.time_ns()`, `Date.now()` or any other wall-clock
function for regulatory timestamps. A static-analysis check (Spotless +
custom rule for Java; ruff custom rule for Python; eslint rule for TS)
SHOULD enforce this; reviewers MUST enforce it on PRs where the static
check is absent.

In production-shadow and production environments, trading-floor servers
MUST be synchronised via a hardware grandmaster (Meinberg LANTIME or
equivalent) with PTP boundary clocks per cabinet and HW-timestamping
NICs (Solarflare or Mellanox), keeping per-server divergence ≤ 100µs to
UTC and logged at 1µs granularity. Local-dev and CI MAY use the bundled
software PTP simulator and `chrony`.

The annual RTS-25 audit pack MUST be produced by `tools/ptp-audit-report/`
from the daily PTP / NTP logs; the resulting PDF MUST carry a verifiable
signature.

**Rationale**: MiFID-II RTS-25 and FINMA expectations make
time-synchronisation a regulator-blocking concern. A platform that is
casual about timestamps cannot ship into a Swiss bank. Treating the clock
as a domain concept with a typed abstraction also eliminates an entire
category of subtle correctness bugs.

### V. Drop-Copy as Source of Truth

For every venue that exposes a drop-copy feed (SIX, Eurex, Tradeweb,
MarketAxess, BidFX, Bloomberg EMSX), the drop-copy stream is the
**authoritative** record of executions. The reconciler service MUST join
the OMS execution stream and the drop-copy stream on the documented
composite key and MUST resolve every disagreement in favour of the
drop-copy.

A drop-copy fill that does not appear in the OMS event store within a
configurable reconciliation window MUST cause the OMS state to be
amended (with audit-chain evidence). The reverse is also true: an OMS
fill that does not appear in drop-copy MUST raise an alert and trigger
investigation.

Recovery from a non-trivial OMS outage MUST be possible from drop-copy
alone; this scenario has its own runbook and is exercised by the chaos
suite.

For venues that do not provide drop-copy (currently Refinitiv as
market-data-only and CFETS via proxy), the platform MUST document the
fallback authority (typically the venue session or the proxy stream) in
ADR `0xxx-drop-copy-venue-matrix.md`.

**Rationale**: Drop-copy as source-of-truth is the architectural pattern
every experienced trading engineer recognises immediately and the one
front-end-tool engineers most often miss. It is what makes recovery
from a 50-minute OMS outage a tractable problem rather than a
career-ending one.

### VI. Append-Only Audit (NON-NEGOTIABLE)

Every command that changes platform state — order submission, cancel,
replace, kill-switch trip, kill-switch reset, entitlement grant or
revocation, schema change applied at runtime, configuration override,
manual reporting trigger — MUST emit an `AuditEvent` to Kafka topic
`audit.command.v1` with a SHA-256 hash chain (`hash = SHA256(prev_hash || canonical(payload))`).

Audit events MUST be retained for at least 5 years (RTS-24 baseline) and
configurable up to 10 years where FINMA requires. After the active
window, audit events MUST be tiered to S3 / MinIO Object Lock with WORM
retention.

The hash chain MUST be verified daily; any mismatch is a Sev-1 incident.
Per-region chains are joined at audit-pack time; the regulator-facing
report verifies each region independently and concatenates by `bizTime`.

There MUST be no destructive deletion of audit data within the retention
window. Pseudonymisation for GDPR is permitted at the analytics
boundary, but the canonical audit chain remains inviolate.

**Rationale**: The audit log is what stands behind every regulatory
filing, every internal investigation, and every customer dispute. If it
is corruptible, the platform cannot be trusted. Hash-chained,
append-only, WORM-archived audit is the minimum bar.

### VII. Test-First for Protocol Code (NON-NEGOTIABLE)

For every codec (FIX, FIXML, FpML, SBE, Avro, ISO 20022), every state
machine (OrdStatus, FixSession, ClearingTrade, KillZone), every domain
invariant (latency-tier placement, sequence-number monotonicity,
hash-chain consistency), and every regulator schema mapping, a
property-based test (jqwik for Java, Hypothesis for Python) MUST exist
and MUST be merged in the same pull request as the implementation. The
test MUST fail before the implementation is written, succeed after, and
remain in CI thereafter.

Conformance tests against the bundled mocks (FIXimulator, Apache Qpid
Broker-J, Bloomberg stub, Refinitiv local IProvider, SIX MTS stub) MUST
exist for every adapter that touches a venue or clearing house, and
MUST run in the conformance CI stage.

Pre-trade risk evaluation has performance gates (p99 < 50µs in JMH) that
also MUST run in CI; performance regressions > 20% against the previous
main build mark the PR as a `performance-regression` and block merge
unless explicitly justified.

**Rationale**: Protocol code is unforgiving — a single tag-9 / tag-10
miscount, a single SBE template-id collision, a single state-machine
edge-case can take a trading day offline. Property-based tests are the
only test style with the coverage density to defend protocol code at
scale. Conformance tests close the gap between "the codec is correct"
and "the venue accepts our messages."

## Architectural Constraints

The following constraints are derived from the principles above and are
binding on every PR:

1. **Code-ownership boundaries**: `apps/venue-adapter-*`, `apps/clearing-adapter-*`,
   and any other adapter MUST NOT export any venue-specific type to a
   downstream service. Module visibility rules (Java module-info,
   Python `__all__`, TS export controls) enforce this.

2. **Mono-repo build cohesion**: The repository's primary build driver
   is Gradle 8.10 (multi-project) coordinated with uv (Python),
   `go.work` (Go), and Cargo (optional Rust) under a top-level
   `Makefile`. New languages or new top-level workspaces require an ADR.

3. **Production-shadow as the deployment depth target**: Local-dev and
   UAT MAY use mocks for external integrations; production-shadow MUST
   integrate with real OSS infrastructure (Postgres, Kafka, Keycloak,
   OpenBao, Linkerd) and either real or vendor-sandbox external
   integrations. Hardware PTP, real WORM with retention lock, and
   bare-metal co-lo for hot-path adapters are mandatory at
   production-shadow depth.

4. **Four-region active-active**: The platform deploys active-active
   across Zurich (ZH4/ZH5), London (LD4), New York (NY4), and Tokyo
   (TY3). Aeron Cluster is per-region (Raft); Kafka, Postgres, and the
   cold-path event store replicate cross-region (MirrorMaker 2 + Aurora
   Global Database + S3 cross-region replication). Single-region failure
   tolerance: RPO ≤ 5s, RTO ≤ 60s.

5. **Secrets, mTLS, identity**: No raw secrets in source control; all
   secrets through OpenBao with audit logging. All in-mesh
   service-to-service traffic mTLS via Linkerd + SPIFFE/SPIRE. All
   external-venue connections TLS 1.3 with cert-manager-driven rotation
   and a 30-day expiry alert.

6. **Schema validation at boundaries**: Inbound messages from external
   systems MUST be validated against the registered schema. Unknown
   fields MUST be logged and surfaced to operations without halting
   processing.

7. **Latency-tier topic naming**: Kafka topics follow
   `<tier>.<context>.<event>.v<n>`. Producers and consumers cross-check
   the tier prefix matches their own tier (warm-tier producer cannot
   publish to a `cold.*` topic without an explicit handoff).

## Development Workflow & Quality Gates

1. **Specification flow**: `/speckit.specify` → `/speckit.clarify` →
   `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`. The plan
   step MUST run a Constitution Check against each of the seven
   principles above; deviations require a Complexity Tracking entry.

2. **Continuous integration matrix**: Every pull request runs lint →
   unit → integration → conformance → performance → security stages.
   Performance is non-blocking but publishes regression tracking.
   Security blocks merge on any HIGH or CRITICAL CVE in trading-path
   containers. Merge to `main` triggers the `deploy-dev` Helmfile sync.

3. **Pull-request review**: Every PR is reviewed by at least one engineer
   outside the PR author's immediate sub-team. Schema changes require
   review by a contracts owner. Hot-path code changes require review by
   a hot-path owner. Audit-chain or time-sync changes require review by
   a regulatory owner.

4. **Architecture Decision Records (ADRs)**: Every decision that
   materially shapes the platform — new venue, new commercial drop-in,
   new latency-tier placement, new regulator interface, change to a
   constitution principle — is recorded as a MADR document under
   `docs/decisions/`. ADR numbering is monotonic.

5. **Runbooks**: Every operational scenario that has caused or is
   plausibly likely to cause a paging event has a runbook under
   `ops/runbooks/`. Chaos tests verify that the documented runbook
   actually works.

6. **Definition of done**: A change is "done" when (a) it is merged to
   main, (b) all CI gates pass, (c) any new schema has a contract test,
   (d) any change to hot-path latency budgets has a JMH bench, (e) any
   change to time-sync, audit, or drop-copy semantics has been signed
   off by a regulatory owner, (f) the relevant runbook (if applicable)
   has been updated.

## Governance

This constitution supersedes informal practice. All pull requests, all
code reviews, and all architecture review-board sessions MUST verify
compliance with the seven principles above and the binding
architectural constraints in `Architectural Constraints`.

**Amendment procedure**: A change to this constitution requires:

1. an ADR in `docs/decisions/` describing the proposed amendment, the
   rationale, the alternatives considered, and the migration plan;
2. a pull request that updates `.specify/memory/constitution.md` and
   any dependent templates / runtime guidance;
3. review and approval by at least two architecture-review-board members;
4. a version bump per the policy below;
5. a Sync Impact Report appended (HTML comment) to the constitution file.

**Versioning policy**:

- **MAJOR**: backward-incompatible governance or principle removals,
  redefinitions, or new NON-NEGOTIABLE principles.
- **MINOR**: new principle or new section added, or material expansion
  of existing guidance.
- **PATCH**: clarification, wording fix, typo correction, or
  non-semantic refinement.

**Compliance review**: A quarterly architecture review MUST audit a
random sample of recent PRs against this constitution and report
findings to the engineering organisation. Recurring violation patterns
trigger either (a) tooling work to make the principle automatically
enforceable, or (b) an amendment that revises the principle.

**Runtime guidance**: Day-to-day development guidance lives in the
agent-context file at the repository root (`CLAUDE.md`). That file MUST
remain consistent with this constitution; conflicts resolve in favour
of the constitution.
